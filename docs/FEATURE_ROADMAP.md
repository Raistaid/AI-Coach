# Aimo: анализ и развитие функций

Дата: 25 октября 2026 года. Основание: чтение актуальных `AGENTS.md`, `README.md`,
`docs/PROMPT.md`, `docs/TEST_PLAN.md`, `app.js`, `coach-engine.js`,
`coach-planner.js` и модулей `skills/`. Это оценка проекта по коду и журналу;
проверка физических телефонов и качества распознавания здесь не выполнялась.

## Что уже есть

- Три работающих модуля навыков: чеканка, приседания, баланс; переходы по
  наблюдениям, ручной пропуск шага, три характера тренера.
- Чат подбора навыков с маршрутом из существующего каталога, локальная LLM
  с проверкой ответа и резервный подбор по ключевым словам.
- Лента подсказок, голос, звуковые сигналы, режим «Крупно» и автоматическое
  переключение по расстоянию; запрос Screen Wake Lock уже есть в `beginLive()`.
- Анализ камеры и локального видео, отдельная симуляция, итог, локальная история
  до восьми записей, пауза и освобождение ресурсов при уходе.

Эти функции нужно проверять и улучшать, а не предлагать как новые.
Сильная сторона продукта — тренер ведёт по наблюдаемым шагам прямо во время
движения. Расширение каталога без проверки реальным видео ослабит эту сторону.

## Подтверждённые пробелы

1. В прежней схеме истории нет `source`, `metricKey`, `schemaVersion`.
   `stopSession()` сохраняет и камеру, и файл. Надёжно восстановить источник
   старых записей нельзя; демо уже исключено из истории.
2. Итог вычисляет последний и следующий урок через количество выполненных
   шагов (`lessonsDone`). После ручного пропуска это количество перестаёт
   совпадать с индексом урока. В `engine.session` есть точные
   `completedLessons`, `skippedLessons` и `lessonIndex`.
3. `mainMistake()` использует `tagCounts`, которые увеличиваются в `emit()`
   при выдаче подсказки. Это количество выданных подсказок с паузами и
   приоритетами, а не частота всех ошибок в наблюдениях. Подпись «замечено
   N раз» и адаптация по таким числам требуют уточнения.
4. Есть `timing.poseMs` и адаптивный интервал детектора мяча, но нет записи
   фактических кадров анализа в секунду за скользящее окно. Чтение кода не
   доказывает выполнение требования 8 кадров/с на телефоне.
5. В `docs/demo/` находится инструкция подготовки видео, а самого запасного
   видео в репозитории нет. CDN-кеш сам по себе не подтверждает готовность
   всей тренировки без сети. Большинство сценариев камеры и мобильной LLM
   остаётся со статусом «Не проверено» в плане приёмки.

## Приёмка и ограничения

### 1. Точный итог после пропусков

Приёмка: выполнить первый шаг, пропустить второй, остановить на третьем.
Итог перечисляет фактически выполненный и пропущенный шаги и предлагает
фактический незавершённый шаг. Пропуск не увеличивает число выполненных.
Ограничение: статус прохождения и разрешение перехода к следующему навыку
маршрута должны учитывать пропуски по одному согласованному правилу.

### 2. Наблюдения и подсказки

Приёмка первого небольшого изменения: вместо «замечено N раз» явно указать
«выдано N подсказок» там, где источником остаётся `tagCounts`. Затем добавить
отдельные счётчики эпизодов ошибок с гистерезисом и знаменателем наблюдения.
Серия одинаковых кадров не становится сотней независимых ошибок.
Ограничение: сравнение разных длительностей по сырому количеству подсказок
не доказывает улучшение техники. До отдельной проверки нельзя использовать
такую статистику как оценку точности или риска травмы.

### 3. Проверка кадра

Приёмка: после явного включения камеры приложение помогает поставить телефон
и сообщает, какая часть тела не видна. Готовность появляется после устойчивой
видимости, а краткое мерцание точек не переключает экран. Отсутствие мяча
не мешает урокам без мяча; на уроке с мячом статус мяча показан отдельно.
Ограничение: не определять безопасность помещения, покрытие или медицинскую
готовность человека по уверенности модели. Не запускать камеру автоматически.

### 4. Частота анализа

Приёмка: на реальном устройстве измерить фактически завершённые анализы за
скользящее окно, полную стоимость кадра и пропуски очереди LLM. При нагрузке
сначала снижать частоту детектора мяча и пропускать генерацию; фиксировать
модель телефона, браузер и настройки. Честно показывать, когда 8 кадров/с
не достигнуты.
Ограничение: длительность только `detectForVideo` позы не равна общей частоте
анализа с отрисовкой и другими моделями. Нужен физический телефон.

### 5. Сравнение прогресса — первая разработанная фича

Контракт новой записи: `schemaVersion: 2`, явный `source`, `metricKey`, ISO-дата,
положительная длительность, целочисленные неотрицательные результаты.
`compareProgress(record, previousRecords)` — чистая функция. Root передаёт
историю до добавления текущей записи.

Приёмка:

- Сравнивается один навык, один источник и одна метрика. Касания и подъёмы,
  камера и файл не смешиваются; симуляция не участвует.
- В чеканке сравнивается лучшая серия `bestStreak`; для подъёмов и приседаний
  — число засчитанных движений, для баланса — лучшее непрерывное удержание.
- Предыдущий результат выбирается по дате, а не по позиции в массиве.
  Записи с той же или будущей датой не считаются предыдущей тренировкой.
- В первой записи нет выдуманной дельты и заявления о новом рекорде.
  Нулевой результат не объявляется рекордом. Равенство рекорду — не новый рекорд.
- Неизвестный источник старой записи не угадывается. Она остаётся видимой
  в истории, но не участвует в сравнении.
- Видео явно помечено «Видео». Текст ограничивает лучшее доступной историей:
  «среди сохранённых тренировок». Сравнение количества не оценивает технику.

Ограничения: root сохраняет максимум восемь записей; это окно истории, а не
результат за всё время. Общее количество повторов зависит от длительности
сессии; сравнение сообщает изменение количества, не улучшение физической формы.
Повторный анализ одного файла остаётся повторным разбором видео.

Проверка модуля 25 октября: 12 тестов, 12 PASS, 0 ошибок. Команда:

```sh
/private/tmp/node-v22.12.0-darwin-arm64/bin/node --test progress.test.mjs
```

Покрыты первая запись, серии вместо суммарных касаний, порядок дат, равенство
и снижение, разные метрики/навыки/источники, симуляция, legacy, отсутствие
засчитанных движений, некорректные числа и даты, часовые пояса, неизменяемость
входа. Root подключил сравнение к итогу и истории. В Chrome проверены старые
записи, отдельная история с синтетическими результатами и завершение демо без
сохранения и сравнения. Полный набор проекта: 58 тестов, 0 падений. Проверка
записи через реальную камеру на физическом телефоне ещё не выполнена.

### 6. Продолжение урока

Приёмка: после перезагрузки видны выполненные, пропущенные и незавершённые
шаги. «Продолжить» сначала повторяет короткую проверку кадра, затем открывает
нужный шаг. Новая сессия не наследует старые касания и фазы движения.
Ограничение: требуется версия схемы уроков и правила инвалидирования прогресса
при изменении `skills/*`. Зависит от задачи 1.

### 7. Ключевые моменты видео

Приёмка: для открытого пользователем файла показать моменты первого касания,
лучшей серии, падения и смены урока. Нажатие переводит временную позицию
исходного видео к событию, пока файл открыт; повторный просмотр не удваивает
результаты тренировки.
Ограничение: журнал хранит только время, тип события и числа. Нельзя записывать
кадры или сохранять видео без нового явного решения. Время файла и время
активной тренировки требуют отдельного сопоставления.

### 8. Практика одной ошибки

Приёмка: тренер объясняет наблюдение («подсказка про высоту стопы повторялась»)
и предлагает конкретный существующий шаг, который можно повторить.
Переход происходит по нажатию; результаты следующей попытки показываются
отдельно. LLM формулирует объяснение только по проверенной сводке.
Ограничение: зависит от задач 1 и 2; адаптация не должна создавать упражнение
из текста модели и не должна выдавать частоту речи за частоту ошибок.

### 9. Левая и правая стопа

Приёмка: касание получает сторону только если траектория мяча уверенно
сопоставлена с одной стопой. Есть состояние «сторона не определена»; сумма
левых, правых и неопределённых касаний равна общему числу. Зеркальный режим
не меняет анатомическую сторону.
Ограничение: нужны тестовые видео, пересечения ног и случаи, когда мяч между
стопами. Близость к стопе не гарантирует реальное касание этой стопой.

### 10. Личная цель

Приёмка: пользователь выбирает цель внутри существующего проверенного
упражнения; например, повторить ранее засчитанную серию. Цель и её выполнение
основаны на той же метрике и явном источнике. Нет штрафа за пропуск дня.
Ограничение: не предписывать рост нагрузки, не обещать результат за срок,
не повышать цели автоматически по одному удачному наблюдению. Историю
восьми записей нельзя использовать для достоверного календаря регулярности.

### 11. Готовность к защите

Приёмка: отдельно указаны доступность камеры, готовность зрения, готовность
опциональной LLM и наличие локального тестового видео на демо-устройстве.
После контролируемого отключения сети команда вручную проходит сценарий
и записывает фактический результат. Без такой проверки нет зелёной отметки
«работает офлайн».
Ограничение: `hasModelInCache` проверяет кеш конкретной LLM, не всю цепочку
CDN/WASM/моделей. Если понадобится Service Worker, сначала проверить его API
и стратегию версионирования; ресурсами браузера и квотой управляет браузер.

### 12. Карточка результата

Приёмка: локально сформировать карточку/текст для скачивания с навыком,
датой, источником, фактической метрикой и выполненными шагами. Для демо
постоянно видна метка симуляции; такая карточка не становится записью истории.
Ограничение: не добавлять проценты точности, рейтинг спортсмена, калории
или медицинские выводы. Отправка в социальные сети остаётся действием человека.

## Роль агента feature_developer

Агент придумывает функции по реальным пробелам и доводит одну выбранную
фичу до проверяемого модуля с тестами. Перед реализацией сообщает root:
проблему пользователя, критерий жюри, контракт данных, список файлов,
приёмку, ограничения и зависимости. Root согласует интеграцию с владельцами
файлов по `AGENTS.md`; общий `app.js` и публикация остаются у root.

Для каждой итерации: прочитать актуальный код → сравнить идею с существующими
функциями → выбрать ограниченную задачу → реализовать чистую логику → выполнить
тесты → передать root контракт и результат → отдельно проверить UI и телефон.
Никаких новых зависимостей, серверов, ключей, кадров в истории и фоновой
публикации в первой итерации. Статус тестов и ограничения записывать по факту.
